# 코인별 매매일지 UX 정리 — 설계 스펙

## 배경

매매일지 페이지(`/journal`, `frontend/components/JournalPage.tsx` +
`frontend/components/JournalMarketDetail.tsx`)의 "코인별 매매일지" 영역에서
사용자가 다음 문제를 지적했다:

1. 진입/청산 시각이 KST로 안 보이는 것 같다.
2. 거래 건수가 많아지면 매매일지 리스트가 아래로 한없이 길어져 페이지 전체가
   늘어난다.
3. 코인별 매매일지에는 달력(캘린더)이 굳이 필요 없다(계좌 전체 요약 쪽
   달력은 유지).
4. "백테스트 vs 실매매" 4개 지표 비교가 공간을 너무 많이 차지한다.
5. 리스트 UX를 손볼 때 손익 숫자에 색상(수익=빨강/손실=파랑)을 넣고,
   진입/청산가는 그대로 두되 수량(`× qty`) 표기는 뺀다.

브레인스토밍 중 모바일 목업 2건(무한스크롤 방지 방식, 백테스트 비교 축약
방식)을 비교해 각각 A안으로 확정했다.

## 목표

1. `entry_time`/`exit_time` 표기를 실제 KST로 정확히 고친다(현재는 UTC로
   보일 가능성이 있는 버그).
2. 매매일지 리스트를 고정 높이 스크롤박스 안에 넣어 페이지 길이가 거래
   건수에 비례해 늘어나지 않게 한다.
3. 코인별 매매일지에서 달력을 제거한다(계좌 전체 요약의 달력은 유지).
4. "백테스트 vs 실매매" 비교를 한 줄짜리 압축 스탯 바로 바꿔 공간을
   최소화한다.
5. 매매일지 리스트 각 행의 손익에 부호 기반 색상(수익 빨강/손실
   파랑)을 넣고, 수량(`× qty`) 표기를 없앤다.

## 비범위

- 색상 코딩은 매매일지 리스트 행에만 적용한다. 계좌 전체 요약 카드의
  누적손익, 코인별 요약 카드의 누적손익 등 다른 pnl 표시는 이번에
  건드리지 않는다(사용자 확정).
- 코인별 매매일지의 백엔드 응답 필드(`daily`, `daily_pnl_30d`)는 그대로
  둔다 — 프론트에서 렌더링만 안 할 뿐, API 계약은 바꾸지 않는다(스코프
  최소화, 계좌 전체 요약 쪽은 같은 필드를 계속 씀).
- `entry_time`/`exit_time`을 만드는 백엔드(`trading/db.py`의
  `datetime('now')`) 자체는 바꾸지 않는다 — DB에는 계속 타임존 마커 없는
  UTC 문자열을 저장하고, 프론트 파싱 쪽에서만 "마커 없으면 UTC로 간주"
  하도록 고친다(마이그레이션 불필요, 기존 저장값과도 호환).
- 무한스크롤 방지/백테스트 비교 축약과 무관한 다른 화면(백테스트 상세,
  그리드서치 이력 등)의 리스트 UX는 이번 스코프가 아니다. 단, ①의
  `formatDateTime`/`formatDateTimeShort` 수정은 공용 함수라 그 화면들의
  타임스탬프 표기도 부수적으로 함께 정확해진다(의도된 부작용, 별도 확인
  불필요).

## 설계

### 1. KST 시간 표기 수정 — `frontend/lib/format.ts`

`formatDateTime`/`formatDateTimeShort`는 `new Date(iso)`로 파싱한 뒤
`Asia/Seoul` 기준 `Intl.DateTimeFormat`으로 변환한다. 문제는 백엔드가
SQLite `datetime('now')`로 저장한 문자열("2026-09-06 05:30:00")에
타임존 마커가 전혀 없다는 것 — 이런 date-time 문자열은 브라우저가 UTC가
아니라 **로컬 시간**으로 해석한다(ECMAScript Date Time String Format
규칙). 그 결과 실제로는 UTC 값인데 이미 KST인 것처럼 취급되어 버린다.

수정: 두 함수 모두, `new Date(iso)` 호출 전에 `iso`에 타임존 마커
(`Z`, `+HH:MM`, `-HH:MM`)가 없으면 UTC로 명시한다.

```ts
function toUtcDate(iso: string): Date {
  const hasTz = /[Zz]|[+-]\d{2}:\d{2}$/.test(iso);
  return new Date(hasTz ? iso : `${iso.replace(' ', 'T')}Z`);
}
```

`formatDateTime`/`formatDateTimeShort` 내부의 `new Date(iso)`를
`toUtcDate(iso)`로 교체한다. 이미 `Z`/오프셋이 붙은 문자열(있다면)은
그대로 통과하므로 회귀 없음.

### 2. 매매일지 리스트 — 고정 높이 스크롤박스

`JournalMarketDetailView`의 "매매일지" 섹션(데스크톱 테이블 +
모바일 카드 두 마크업 모두)을 `max-height`를 준 컨테이너로 감싸고
`overflow-y-auto`를 건다. `max-height`는 모바일 카드 기준 3~4건 정도가
보이는 높이(대략 `320px` 안팎, 실제 구현 시 카드 한 개 실측 높이로
미세조정)로 잡는다. 섹션 제목 옆에 "전체 N건"을 표기한다
(`detail.trade_log.length`). 반응형 분기(데스크톱 테이블/모바일 카드)
구조 자체는 유지하고, 그 바깥을 스크롤 컨테이너로 감싸기만 한다.

### 3. 코인별 매매일지 달력 제거

`JournalPage.tsx`에서 `selectedMarket` 상세를 렌더링하는 블록의
`<JournalCalendar daily={detail.daily} />` 호출(현재 168번째 줄)을
삭제한다. 계좌 전체 요약 쪽의 `<JournalCalendar daily={summary.daily} />`
(143번째 줄)는 그대로 둔다.

### 4. 백테스트 vs 실매매 — 한 줄 압축 스탯 바

`JournalMarketDetailView`의 "백테스트 vs 실매매" 섹션에서 현재의
`hidden md:block` 테이블 + `md:hidden` 2x2 카드 그리드(두 벌 마크업)를
제거하고, 반응형 분기 없이 항상 같은 한 줄짜리 컴팩트 컴포넌트로
대체한다:

```
승률 45%→50%   평균수익률 1.2%→0.8%   MDD -5%→-6%   거래 30→8건
```

각 항목은 `라벨` + `백테스트값 → 실매매값`. 목업 A안 그대로: `flex`
한 줄에 4개 항목을 균등 배분, 폰트는 기존 대비 작게. 화면 폭이 좁아
줄바꿈이 필요하면 `flex-wrap`으로 자연스럽게 두 줄까지는 허용(가로
스크롤은 만들지 않음).

`comparison === null`(백테스트 비교 불가) 케이스와
`sample_size_warning` 문구는 기존 그대로 유지한다.

### 5. 색상 코딩 + 수량 표기 제거

매매일지 리스트 각 행에서 `realized_pnl` 부호로 클래스 결정:
`realized_pnl >= 0` → 빨강(수익), `realized_pnl < 0` → 파랑(손실).
`close_reason`과는 무관(손절이든 매도신호든 서킷브레이커든 손실이면
파랑). 데스크톱 테이블/모바일 카드 두 곳 모두 적용.

진입/청산 표기에서 `{price}원 × {qty}` 형태를 `{price}원`으로 바꿔
수량을 뺀다(`entry_qty`/`exit_qty` 자체는 타입/응답에서 안 지운다 —
화면에서만 안 보여줌).

## 테스트 계획

- `toUtcDate`(신규 유틸) 단위 테스트: 마커 없는 문자열 → UTC로 처리되어
  KST 변환 시 9시간 차이가 나는지, 이미 `Z`/오프셋 있는 문자열은 그대로
  파싱되는지.
- `JournalMarketDetailView` 렌더 테스트(기존 테스트가 있다면 확장,
  없다면 신규): 색상 클래스가 손익 부호대로 붙는지, 수량 문구가 안
  보이는지, 스크롤 컨테이너가 존재하는지, 압축 스탯 바에 4개 지표가 다
  나오는지.
- 브라우저 수동 확인(모바일 뷰포트): 거래 10건 이상인 코인으로 실제
  스크롤 동작, 시간 표기가 실제 KST와 맞는지 육안 대조.
