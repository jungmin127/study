# 라이브 트레이딩 로드맵 — 작업 순서 확정 (2026-08-09)

이 문서는 새 아키텍처 결정을 담은 스펙이 아니라, `2026-08-04-live-trading-foundation-design.md`가
정의한 0~4단계 로드맵을 **지금부터 어떤 순서로 진행할지** 사용자와 합의한 내용을 기록한다.
스펙/플랜 자체를 재논의할 필요가 생기면 원본 스펙과 각 서브플랜 문서를 참고할 것 — 이 문서는
순서만 다룬다.

## 배경

1단계(트레이딩 엔진 + 핵심 안전장치)는 서브플랜 ①②③④⑤-1~⑤-4c까지 구현이 끝났고, ⑤-4c는
7라운드 리뷰를 거쳐 Critical은 전부 해소됐지만 Important 5건 + Minor 3건이 백로그로 남아있다
([[upbit-v1-realtime-risk-exit-postmortem]] 참고). 사용자가 "소액이라도 자동매매가 실제로
도는 걸 먼저 보고 싶다"는 목표를 밝혔고, 그 목표는 4단계(운영 하드닝)가 아니라 **1단계 스펙
자체가 이미 요구하는 항목**(결정5 보완조치: "실전 투입 전 최소주문금액 규모의 소액 실전
테스트를 1단계 플랜의 필수 검증 단계로 포함한다")이라는 걸 확인했다. 그래서 4단계로
건너뛰지 않고 1단계부터 완전히 마무리하기로 확정.

## 확정된 작업 순서

### 1. 1단계 완결 (지금부터 진행)

1. **⑤-4c 백로그 8건 (Important 5 + Minor 3)** — `trading/order_executor.py`의
   `exit_for_risk`/`_resolve_stale_ask_order` 영역. 잔여 미체결 주문 취소 후 체결 정보가
   `realized_pnl`/`current_capital`/reconciler에 제대로 안 넘어가는 게 공통 원인(자금
   정확성 버그라 실거래 전 반드시 고쳐야 함). 상세 목록: [[upbit-v1-realtime-risk-exit-postmortem]].
2. **이월된 운영 가시성/데이터 무결성 항목** — ⑤-1~⑤-4b 각 서브플랜 최종리뷰가 후속
   서브플랜으로 넘긴 것들 중 아직 아무도 안 건드린 것. 확인된 것: `upbit_ws.py`/
   `upbit_client.py` 로깅 전무, `signals` 테이블 UNIQUE 제약 없음, `skip_reason` 값
   도메인이 `"unknown"` 하나뿐, `circuit_breaker_state.resumed_at` 포맷 불일치(KST/UTC)
   + 감사 컬럼으로 미완성, `db._connect()`가 호출마다 스키마 재실행. 소액이라도 실거래
   중 문제가 생기면 로그 없이는 원인 파악이 안 되므로 소액 테스트 전에 처리.
3. **⑥ 승인/제어 UX** — 라이브 전략 관리 API + 프론트엔드. 이게 있어야 "전략 승인" 흐름을
   DB 직접 SQL 없이 자연스럽게 탈 수 있다. `daemon.py`는 `live_strategies.status` 컬럼만
   읽는 계약이므로 ⑥이 그 컬럼에 쓰기만 하면 daemon 쪽 변경 없이 그대로 동작해야 한다.
4. **소액 실전 테스트 실행 (10만원 규모)** — 스펙 결정5 보완조치가 명시한 1단계의 마지막
   관문. **PC/daemon을 켜놓고 직접 지켜보면서 진행** — 포지션이 열려있는 동안 PC를 끄면
   ticker 기반 손절/익절과 캔들 기반 매도신호가 전부 멈춰서 포지션이 무방비로 노출된다
   (daemon이 살아있어야만 작동하는 앱 레벨 감시 방식이지, 거래소에 걸어두는 예약주문이
   아님). 이 제약은 아래 2번(상시 서버 배포) 전까지 계속 유효.

여기까지 끝나야 스펙이 정의한 1단계("승인된 전략 여러 개가 실제 자금으로 안전하게 동시
자동매매되는 최소 시스템")가 완전히 검증된다.

### 2. 4단계 — 상시 서버 배포 (PM2/Docker)

1단계 완결 후 진행. "PC를 꺼도 자동매매가 계속 돈다"를 실제로 만족시키려면 daemon을 24/7
켜져 있는 별도 서버(클라우드 VPS 등)에 올려야 한다 — PM2/Docker는 그 서버 위에서 프로세스
생존을 관리하는 도구일 뿐, PC 전원 자체가 꺼지면 무력하다는 걸 사용자와 확인했다. 즉 4단계의
본질은 "배포 스크립트 작성"이 아니라 "daemon이 상주할 상시 가동 호스트를 마련하는 것"이다.
업비트 API Open IP 등록도 이 단계에서 (호스트가 바뀌면) 재확인 필요.

지표 커버리지 확장/부하·장기구동 테스트 등 4단계의 나머지 범위는 원본 스펙
(`2026-08-04-live-trading-foundation-design.md`) 로드맵 표 참고.

### 3. 2단계(텔레그램 제어/알림) + 3단계(분석 대시보드) — 후순위

4단계까지 끝난 뒤 진행. 순서만 바뀌었을 뿐 원본 스펙의 범위 정의는 그대로 유효.
