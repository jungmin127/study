# 장세 fact 라벨 기반 백테스트 성과 분석 — 설계 스펙 (Phase 1)

## 배경

`docs/regime-ml-backlog.md`의 우선순위 1번 항목. "장세에 따라 전략을 갈아 끼우면 실제로
수익이 개선되는가"라는 핵심 가설을, ML 예측(불완전, walk-forward pooled weighted kappa
0.097)이 아니라 **사후 확정 사실(fact)** 로 먼저 검증한다. `engine/regime_ml_labels.py:compute_triple_barrier_labels()`는 학습 라벨을 만드는 데 쓰고 있을 뿐 함수 자체는 실제
과거 가격이 상단/하단 경계 중 어느 쪽을 먼저 터치했는지를 판정하는 fact 함수이므로, ML을
전혀 개선하지 않고도 재사용할 수 있다.

이 항목의 결론(장세별로 전략 성과가 실제로 갈리는가)이 백로그 ②(모델 성능 개선)·③(실시간
전략 전환)의 착수 여부를 결정한다 — 갈리지 않으면 ②③에 투자할 근거가 약해진다.

브레인스토밍에서 다음이 확정됐다:

- 검증은 2단계로 진행한다: **Phase 1(이 스펙) = 세그먼트 비교**(저렴, 진단용) →
  Phase 1에서 유의미한 차이가 확인될 때만 **Phase 2 = 오라클 전환 백테스트**(비쌈, 실제
  수익 개선폭 측정)를 별도 세션에서 브레인스토밍한다. Phase 2는 이 스펙의 비범위다.
- Phase 1은 새 백테스트/그리드서치를 돌리지 않고, 이미 DB에 저장된 백테스트 결과의 거래
  기록(`trades_json`)을 재분석한다.
- DB 커버리지를 실측 확인한 결과, `backtest_runs`(97건) 중 `KRW-BTC`/`KRW-XLM`
  `minutes60` 조합이 61건(BTC 41 + XLM 20, 2026-06~08 약 2.5개월)으로 표본이 가장
  두터웠다. 나머지 마켓은 1~2건씩 산발적이라 통계적 설득력이 약함 — 이번 Phase 1은
  **BTC/XLM minutes60 두 마켓으로 범위를 좁혀서 진행**하고, 20마켓 전체 일반화는
  하지 않는다.

## 목표

1. 저장된 BTC/XLM `minutes60` 백테스트 61건의 거래(trade) 각각을 진입 시점의 fact
   라벨(하락/하락아님)로 재분류한다.
2. 하락 진입 거래 vs 하락아님 진입 거래의 성과(승률/평균수익률)가 실제로 다른지
   전체 풀링 기준으로 확인한다.
3. run(전략)별로 "하락 국면에서 잘 맞는 전략"과 "하락아님 국면에서 잘 맞는 전략"의
   순위를 각각 매겨, 두 목록이 얼마나 겹치는지(=최적 전략이 실제로 다른지)를
   확인한다.
4. 사람이 읽고 ②③ 착수 여부를 판단할 수 있는 콘솔 리포트를 출력한다 — 스크립트
   자체는 go/no-go를 자동 판정하지 않는다.

## 비범위

- 새 백테스트/그리드서치 실행 — 기존 저장 결과만 재분석
- BTC/XLM 외 마켓으로의 일반화 — 표본 부족으로 이번 라운드에서 판단하지 않음
- 오라클 전환 백테스트(Phase 2) — 이 스펙의 결론에 따라 착수 여부를 별도 세션에서
  브레인스토밍
- `engine/`, DB 스키마, 프론트엔드 변경 — 순수 읽기 전용 분석 스크립트 하나만 추가
- 통계적 유의성 검정(t-test 등) — 기술 통계(거래수/승률/평균수익률)만으로 1차 판단.
  Phase 1 결과가 애매하면(경계선상) 그때 검정 도입 여부를 다시 판단

## 설계

### 데이터 흐름

새 스크립트 `scripts/analyze_regime_fact_performance.py` (기존 `scripts/select_barrier_k.py`,
`scripts/validate_hmm_feature.py`와 같은 1회성 리포트 스크립트 스타일 — 재실행 가능하게
남겨두되 파이프라인에 자동 연결하지 않음):

1. **라벨 시계열 생성**: `KRW-BTC`, `KRW-XLM`의 `minutes60` 캔들을 `2024-01-01`~현재까지
   `upbit_data_service.get_candles` (또는 `engine.regime_ml_data.load_market_training_data`)로
   가져와 `compute_triple_barrier_labels(df, half_life_bars, n_bars, k)`를 적용한다.
   `half_life_bars = half_life_bars_for_timeframe("minutes60")`(=24),
   `n_bars = round(half_life_bars * N_MULTIPLIER)`(=60), `k = 6.25` — 전부
   `engine/regime_math.py`/`scripts/train_regime_ml.py`의 프로덕션 상수를 그대로 가져와
   쓴다(새 값을 정하지 않는다). 시작일을 61건의 최초 시작일(2026-06-05)보다 훨씬 앞선
   `2024-01-01`로 잡는 이유는 EWM 변동성 warm-up을 충분히 확보하기 위함이고, 끝을
   "현재"로 잡는 이유는 마지막 거래들도 `n_bars`(60봉) 만큼의 미래 데이터를 확보해
   라벨이 `NaN`이 되지 않게 하기 위함이다.
2. **거래 로드**: `engine.cache.list_backtest_runs(market="KRW-BTC")` /
   `list_backtest_runs(market="KRW-XLM")`로 `timeframe="minutes60"`인 결과만 걸러
   (함수 자체엔 timeframe 필터가 없으므로 호출부에서 `r["timeframe"] == "minutes60"`으로
   추가 필터) 각 run의 `trades`(entryTime, returnRate 등)를 꺼낸다.
3. **라벨 매칭**: 각 거래의 `entryTime`을 해당 마켓 라벨 시계열에 매칭한다(캔들 인덱스에
   `asof`/`searchsorted`로 가장 가까운 과거 바를 찾음 — 거래는 봉 경계에서 진입하므로
   정확히 일치하는 게 정상이나, 미세한 어긋남에 대비해 근사 매칭으로 방어). 라벨이
   `NaN`인 거래(라벨 시계열 끝 60봉 이내 진입)는 제외하고 제외 건수를 로그로 남긴다.
4. **집계 및 출력**:
   - **전체 풀링 비교표**: 하락 진입 vs 하락아님 진입 각각 거래수/승률/평균수익률/
     총수익 기여도
   - **run별 랭킹**: run마다 하락 진입 거래 평균수익률, 하락아님 진입 거래 평균수익률을
     각각 계산해(거래수가 너무 적은 run은 표기만 하고 순위에서 제외하는 최소 거래수
     기준을 둠 — 예: 5건 미만) 하락 기준 상위 10개, 하락아님 기준 상위 10개를 나란히
     출력하고 두 집합의 교집합 개수(overlap)를 표시

### 출력 형식

`select_barrier_k.py`와 동일하게 표준출력 텍스트 표 — 별도 파일 저장이나 DB 기록 없음.
사람이 읽고 판단하는 1회성 리포트이므로 구조화된 리턴값이나 JSON 저장은 만들지 않는다.

### 최소 거래수 기준

run별 랭킹에서 표본이 너무 적은(예: 하락 진입 거래가 5건 미만인) run은 평균수익률의
분산이 커서 랭킹에 넣으면 오해를 유발한다 — 랭킹에서는 제외하되 "표본 부족으로 제외"
목록으로 별도 출력해 데이터가 사라진 게 아님을 보여준다.

## 테스트 전략

순수 분석 스크립트(1회성 리포트)라 `select_barrier_k.py`/`validate_hmm_feature.py`와
동일하게 자동화 테스트를 추가하지 않는다. 라벨 매칭 로직(entryTime → 라벨)이 핵심
정확성 지점이므로, 실행 후 몇 건을 수동으로 추출해 원본 캔들 데이터와 대조해 육안
검증한다(예: 특정 거래 진입 시각 전후 60봉 종가를 직접 찍어보고 라벨이 맞는지 확인).

## 완료 기준

- 스크립트 실행 결과(전체 풀링 비교표 + run별 랭킹 + overlap)를 사용자에게 보여주고,
  "장세별 전략 성과가 실제로 갈리는가"에 대한 1차 결론을 함께 정리한다.
- 백로그 문서(`docs/regime-ml-backlog.md`)에 이번 세션 결과와 ②③ 착수 여부 판단을
  반영해 갱신한다.
