# 그리드서치에서 CPU와 메모리의 역할

`scripts/grid_search.py`가 무엇을 계산하고, CPU/메모리가 각각 어떤 역할을 하는지, 그리고
더 빠르게 하려면 무엇을 증설해야 하는지 정리한 문서. (2026-08-23)

## 무엇을 계산하나

지표 계산(RSI, SMA 등)은 pandas/numpy로 벡터화돼서 빠르게 끝난다. 무거운 부분은 그 뒤다:
조합 하나마다 `backtrader`의 `Cerebro()`를 새로 만들어서 캔들을 한 봉씩 순회하며 매수/매도를
시뮬레이션한다. 이건 파이썬 레벨 반복문에 가까운 구조라 벡터화가 안 되고, 순수 CPU 연산이다.

이걸 조합 수만큼(예: 지표 풀 확장 후 33,453개) 반복한다. 조합 하나하나는 완전히 독립적이라
(하나의 결과가 다른 조합에 영향을 주지 않는다) 워커 프로세스 여러 개에 나눠 돌리는 게 그대로
먹힌다 — 이게 `WORKER_COUNT`다.

## CPU의 역할: 실제 계산

파이썬은 GIL 때문에 스레드로는 이런 CPU 작업을 진짜 병렬로 못 돌린다. `multiprocessing.Pool`로
**별도 프로세스**를 띄우면 각 프로세스가 독립된 코어를 온전히 쓸 수 있다. 그래서 워커 수를
늘리면(=더 많은 코어를 쓰면) 처리 속도가 그대로 따라 올라간다.

**실측(2026-08-23, 물리 6코어/12스레드 머신, 동일 조건 KRW-BTC 그리드)**

| 워커 수 | 처리 속도 (steady-state) |
|---|---|
| 4 | 270.4 combos/min |
| 6 | 471.7 combos/min |

6은 이 머신의 물리 코어 수와 정확히 같아, 하이퍼스레딩 경합 없이 쓸 수 있는 자연스러운
상한이었다.

## 메모리의 역할: 계산을 빠르게 하지 않는다 — "몇 개를 동시에 돌릴 수 있냐"만 결정

메모리는 이 워크로드에서 계산 속도 자체를 올려주지 않는다. 대신 두 가지 역할을 한다:

1. **워커 하나가 뜰 때 기본으로 먹는 양** — 캔들 데이터 자체는 작지만(1,873행 정도), pandas/
   numpy/backtrader를 import하는 것만으로 워커 하나가 뜰 때 ~148MB 정도 잡는다.
2. **backtrader의 메모리 누수를 담을 그릇** — `Cerebro()`를 반복 생성할 때마다 워커 메모리가
   조금씩 샌다(실측 154~175 KB/call). 워커가 이걸 계속 짊어지다가, 일정 횟수
   (`MAX_TASKS_PER_CHILD=5359`)마다 프로세스를 갈아치워서 비운다.

즉 메모리가 부족하면 "워커를 몇 개까지 안전하게 띄울 수 있는가"의 상한이 낮아진다. 그 상한에
걸리면 워커 수를 줄이거나(=속도 저하), 최악의 경우 OOM으로 죽는다. 하지만 메모리가 넉넉하다고
해서 워커 하나의 계산 자체가 빨라지진 않는다 — 병렬로 몇 개 더 안전하게 띄울 여유가 생길
뿐이다.

## 그래서 증설한다면: CPU (정확히는 코어 수)

이 워크로드 기준으로는 **CPU(코어 수)**가 명확히 더 좋은 투자다.

- 지금 이 컴퓨터는 물리 코어 6개 = 워커 6개가 자연스러운 상한이었고, 4→6에서 속도가 그대로
  따라 올라가는 걸 실측으로 확인했다. 코어가 더 있었다면(예: 8코어) 워커를 8개까지 늘려서
  더 빨라질 여지가 있었을 것이다.
- 반대로 메모리는 전혀 병목이 아니었다 — 다른 앱을 끄고 여유 RAM 7.5GB인 상태에서, 워커
  6개가 10분간 다 합쳐도 1.4GB밖에 안 썼다. 지금 RAM을 늘려도 코어 수가 그대로면 워커
  최적 개수도 그대로 6개라 계산 속도엔 변화가 없다.

**정리:** 코어 수를 늘리면 = 워커 수를 그만큼 늘릴 수 있고 = 거의 선형으로 빨라진다. 메모리는
"코어를 늘렸을 때 그만큼의 워커를 안전하게 감당할 수 있느냐"를 뒷받침하는 보조 지표에
가깝다 — 코어를 늘릴 계획이 있을 때 함께 챙기면 된다.
