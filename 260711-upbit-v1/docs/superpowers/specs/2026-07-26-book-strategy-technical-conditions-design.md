# 책 전략에서 이식 가능한 기술적 조건 추가

## 목적
`docs/book_ref/`의 가치투자 백테스트 서적(CAN SLIM, Magic Formula, Piotroski F-Score, Benjamin Graham, Peter Lynch, David Dreman 등)을 검토한 결과, 매수 조건 자체(PER/PBR/ROE/EPS성장률/부채비율 등 재무제표 팩터)는 업비트 코인에 이식할 수 없다(유통주식수/이익/자산 데이터가 없음). 다만 모든 전략에 공통으로 적용되는 기술적 리스크관리 규칙 중 다음 두 가지는 이식 가능하고 실제로 가치가 있다:

1. **최대 보유기간 매도** — 책 예시: "종목을 보유한 지 60거래일 이상이 되면 매도", "최대 5일간 보유".
2. **시장 추세 필터(마켓타이밍)** — 책 예시: "코스닥 지수가 3·5·10일 이동평균보다 하락하면 매매를 쉼". 코인 시장엔 코스닥 같은 지수가 없지만, 알트코인이 BTC 추세를 따라가는 경향을 이용해 KRW-BTC를 시장 대표 지표로 쓴다.

`STOP_LOSS_PCT`/`TAKE_PROFIT_PCT`(손절/익절 %)는 이미 구현되어 있어 이번 작업에서 제외.

## 설계

### 1. HOLDING_PERIOD_BARS (보유기간 매도)
- `STOP_LOSS_PCT`/`TAKE_PROFIT_PCT`와 동일한 "포지션 상태 기반" 패턴. `sellOnly: true`, `fixedOperator: ">="`.
- 단위는 봉(bar) 개수 — 캘린더 일수가 아니다. 타임프레임에 무관하게 일관된 의미를 갖는다(예: 15분봉 20개 = 5시간, 일봉 20개 = 20일).
- `ConditionTreeStrategy`가 포지션 진입 시점의 봉 번호(`len(self)`)를 기억해뒀다가, 매 봉마다 `현재 봉 번호 - 진입 봉 번호`로 보유 봉수를 계산해 `eval_group`에 전달한다.

### 2. MARKET_TREND (BTC 추세 필터)
- 값 = `KRW-BTC 종가 - SMA(KRW-BTC 종가, period)`. 매수/매도 조건 둘 다 사용 가능한 일반 지표(포지션 상태와 무관).
- `engine/runner.py`에 이미 존재하지만 실제로 호출되는 곳이 없던 `PandasDataWithExtra`/`extra_column` 확장포인트(주석: "dominance, kimchi_premium 등 외부 데이터 컬럼")를 되살려 구현한다. `engine/runner.py` 자체는 코드 변경이 필요 없다 — 이미 완성된 채로 방치되어 있었다.
- KRW-BTC는 하드코딩된 시장 대표 지표다(파라미터화하지 않음) — 이번 스코프에서는 다른 마켓을 대표 지표로 쓰는 옵션은 제공하지 않는다.
- 조건식에 `MARKET_TREND`가 실제로 있을 때만 KRW-BTC 캔들을 추가로 조회한다(불필요한 API 호출 방지). 백테스트 대상 마켓이 KRW-BTC 자신이면 별도 조회 없이 자기 종가를 그대로 재사용한다.
- `GET /api/v1/backtests/validate`(사전 검증 엔드포인트)는 BTC 데이터를 별도로 조회하지 않는다 — 필요 최소 봉수(`max_required_period`) 검증은 조건식의 숫자 파라미터만 보고 계산되므로 이미 커버된다. 이는 의도적 설계다(불필요한 API 호출 방지).
- 카테고리는 프론트엔드에 이미 예약되어 있었지만 어떤 지표도 쓰지 않던 "시장 심리"를 사용한다.

## 비범위
- 분할매도(가격 구간별 부분 청산)는 포지션 사이징/체결 로직 자체를 바꿔야 해서 제외.
- 베타/상관계수 기반 종목 선정은 롤링 상관계수 계산이 필요해 제외.
- MARKET_TREND의 기준 마켓(KRW-BTC)을 사용자가 바꿀 수 있는 옵션은 제외.
- 펀더멘털(재무제표) 기반 전략 이식은 애초에 불가능하므로 다루지 않음.

## 검증
- 기존 손절/익절 조건처럼, 두 지표가 조건 빌더 UI에 자동으로 노출되고(카탈로그 순회 구조 덕분에 프론트 코드 변경 최소화) 실제 조건식으로 사용해 백테스트를 실행했을 때 정상 동작하는지 확인한다.
- `MARKET_TREND` 사용 시에만 KRW-BTC 캔들이 추가 조회되고, 사용하지 않을 때는 기존과 동일하게 API 호출이 늘어나지 않는지 확인한다.
