# 4단계 배포 — Oracle → AWS 전환 — Design Spec

## 배경 및 목표

[[upbit-v1-server-deployment-shipped]]에서 4단계(상시 서버 배포) 파일 일체(systemd
유닛/`deploy/setup.sh`/`deploy/update.sh`/`deploy/README.md`)를 이미 만들어 push했다.
그런데 실제 VM 생성 단계에서 사용자가 Oracle Cloud `VM.Standard.A1.Flex`(Ampere ARM
Always Free)를 계속 `API 오류: AD-1 세이프에 대한 용량이 부족합니다`로 만들지 못했다
([[upbit-v1-server-deployment-cloud-provider-decision]]). Oracle Free Tier Ampere A1의
잘 알려진 재고 부족 문제이고, 대안들(PAYG 전환, 유료 셰이프, RAM 1GB 무료 셰이프)을
검토한 끝에 AWS로 전환하기로 이미 결정했다.

이 스펙의 목표는 그 결정을 실제로 반영하는 것이다: **AWS EC2로 VM을 만드는 절차를
`deploy/README.md`에 문서화**하고, AWS 특유의 두 가지(고정 퍼블릭 IP, 크레딧 소진 감시)를
런북에 추가한다. `2026-08-14-live-trading-server-deployment-design.md`(결정 1을 제외한
결정 2~7)는 이미 "우분투 VM이면 클라우드 무관"하게 설계돼 있어 그대로 유효하다 — 이
스펙은 그 결정 1(프로바이더/VM 생성 방식)만 교체한다.

사용자는 AWS 계정을 이미 만들었고(가입 시 크레딧 $100 + 온보딩 과제 완료 시 $100,
6개월간 사용), 구글 OTP로 2단계 인증도 이미 설정했다. 콘솔에서 리전을 "아시아 태평양
(서울)"로 선택해둔 상태도 확인했다.

## 범위

**이 스펙에서 다루는 것:**
- AWS EC2 인스턴스 스펙 확정(리전/인스턴스 타입/AMI/스토리지)
- 고정 퍼블릭 IP 확보 방식(Elastic IP) — 업비트 API 키 IP 화이트리스트가 재부팅마다
  깨지지 않도록
- AWS 보안 그룹 설정(Oracle Security List를 대체) — 기존 "SSH만 인터넷에 노출"
  원칙 유지
- 크레딧 소진 조기 감지용 AWS Budget 알림
- `deploy/README.md`를 AWS EC2 launch wizard 기준으로 재작성

**이 스펙에서 다루지 않는 것(2026-08-14 스펙이 이미 다루고, 변경 없음):**
- systemd로 3개 프로세스 관리하는 방식(결정2) — 그대로
- Tailscale 사설망 원칙(결정3) — 그대로, VM 안에서의 `ufw` 설정도 동일
- CORS `ALLOWED_ORIGIN` 환경변수화(결정4) — 이미 구현·병합됨, 변경 없음
- `deploy/setup.sh`/`deploy/update.sh`의 내용(결정5) — 코드 변경 없음, 그대로 재사용
- 서버가 새 빈 DB로 시작한다는 결정(결정6) — 그대로
- systemd 기본 재시작 정책에 장애 대응을 위임하는 결정(결정7) — 그대로
- IAM 사용자/역할, VPC 커스터마이징, RDS 등 — 이 프로젝트는 SQLite 단일 VM 구성이라
  AWS의 기본 default VPC + 단일 EC2 인스턴스로 충분, 추가 AWS 리소스 불필요

## 핵심 결정

### 결정 1 — AWS EC2, 서울 리전, `t4g.small`(ARM Graviton)

Oracle Ampere A1(재고 부족)의 대체로 AWS EC2를 쓴다. AWS `t2/t3/t4g` 계열은 범용
인스턴스라 재고 부족 문제가 사실상 없다.

- **리전: 아시아 태평양(서울, `ap-northeast-2`)** — 업비트는 한국 거래소이므로 서울
  리전이 API 응답 지연을 최소화한다. 애초 검토했던 싱가포르(`ap-southeast-1`) 대신
  서울로 확정(사용자 콘솔에 이미 설정됨).
- **인스턴스 타입: `t4g.small`(ARM/Graviton, 2 vCPU / 2GB RAM)** — Oracle 대안으로
  검토했던 `E2.1.Micro`(1GB, 무료)는 `npm run build`(Next.js) 메모리 요구량(보통
  1~2GB) 대비 빠듯해 스왑 설정이 추가로 필요했다. `t4g.small`은 2GB라 스왑 없이도
  빌드가 안정적으로 돈다. ARM이라 Oracle A1과 아키텍처가 같아 Python/Node 호환성
  문제가 없다(기존 스펙의 결정1과 동일한 근거). 서울 리전 온디맨드 요금은 대략 월
  $10~13 수준으로 추정(정밀 단가는 배포 시점에 AWS 콘솔에서 재확인) — $200 크레딧
  범위 안에서 6개월 이상 여유 있게 운용 가능.
- **AMI: Ubuntu 22.04 LTS(또는 24.04 LTS) ARM64** — 기존 스펙의 Ubuntu 선택 근거
  그대로(문서/커뮤니티 자료가 가장 많음). AWS Marketplace의 공식 Canonical AMI를 쓴다.
- **스토리지: gp3 20GB** — AWS 기본 Ubuntu AMI 루트 볼륨(8GB)은 `git clone` + 파이썬
  venv + `node_modules` + Next.js 빌드 산출물을 합치면 빠듯하다. gp3 20GB로 늘려도
  월 약 $1.6 수준이라 예산에 미치는 영향은 미미하다.

### 결정 2 — Elastic IP로 퍼블릭 IP를 고정한다

EC2 인스턴스를 중지(stop) 후 재시작하면 기본 퍼블릭 IP가 매번 바뀐다. 업비트 API 키의
IP 화이트리스트가 특정 IP에 묶여 있으므로, IP가 바뀔 때마다 업비트 콘솔에서 재등록해야
하는 건 24/7 운영 목표와 맞지 않는다.

**Elastic IP를 할당해 인스턴스에 연결한다** — 이후 인스턴스를 재시작해도 같은 IP를
유지한다. 2024년부터 AWS가 모든 퍼블릭 IPv4 주소(Elastic IP 포함)에 시간당 과금(약
$0.005/시간, 월 약 $3.6)을 매기기 시작했지만, 이 프로젝트는 24/7 상시 가동이 전제라
어차피 퍼블릭 IP가 항상 붙어있어야 하므로 Elastic IP를 쓰지 않을 때와 비용 차이가
사실상 없다(둘 다 켜져있는 동안은 과금). 대신 IP 안정성이라는 실질적 이득이 있으므로
Elastic IP를 확정한다.

**주의사항(런북에 명시):** 인스턴스를 완전히 중지(stop)한 채로 오래 두면 Elastic IP
과금만 계속 발생하고 서버는 놀고 있는 상태가 된다 — 안 쓸 계획이면 Elastic IP
할당(release)까지 해제해야 한다. 이 프로젝트는 상시 가동이 목적이므로 해당 사항 없음.

### 결정 3 — AWS 보안 그룹으로 기존 "SSH만 개방" 원칙을 유지한다

2026-08-14 스펙 결정3(Tailscale 전용, 공용 인터넷에 backend/frontend 포트 미개방)은
그대로 유지한다. Oracle의 Security List 역할을 AWS에서는 **보안 그룹(Security
Group)**이 담당한다.

- 인바운드: **SSH(TCP 22)만 `0.0.0.0/0`(어디서든) 허용** — 기존 Oracle 설계와 동일한
  원칙(키 인증만 허용, 비밀번호 로그인 비활성은 Ubuntu AMI 기본값). 8000/3000번 포트는
  보안 그룹에서부터 아예 열지 않는다 — VM 내부 `ufw`(결정3의 이중 방어)까지 갈 필요도
  없이 AWS 레벨에서 막힌다.
- 아웃바운드: 기본값(전체 허용) 유지 — 업비트 REST/WS API 호출, `apt`/`npm`/`pip`
  패키지 설치, Tailscale 연결에 필요.
- VM 내부 `ufw` 설정은 2026-08-14 스펙 그대로(`deploy/setup.sh`가 `ufw allow OpenSSH`
  + `ufw enable`) — AWS 보안 그룹과 `ufw`가 이중으로 SSH 외 포트를 막는 구조는 Oracle
  때와 동일하게 유지된다.

### 결정 4 — 키페어는 ED25519, Windows SSH 접속 방법을 런북에 명시한다

EC2 인스턴스 생성 시 새 키페어를 만든다(ED25519 — RSA보다 짧고 최신 OpenSSH가 기본
지원). 콘솔에서 `.pem` 파일을 다운로드한다.

Windows에서 흔히 겪는 문제를 런북에 미리 적어둔다: OpenSSH 클라이언트는 프라이빗 키
파일의 권한이 너무 열려 있으면(`Permissions 0644 for '...pem' are too open`) 접속을
거부한다. Git Bash에서는 `chmod 400 <키파일>.pem`으로 대부분 해결되지만, Windows
파일시스템(NTFS) 특성상 안 먹힐 때는 PowerShell의 `icacls` 대안 명령을 함께 적는다.

### 결정 5 — AWS Budgets Actions로 예산 알림 + "수동 승인" 정지 버튼을 만든다

$200 크레딧(6개월)이 예상보다 빨리 소진되거나, 실수로 다른 리소스를 추가로 만들어
과금이 새는 것을 조기에 알아챌 수 있도록, AWS Budgets에서 **월 $20 초과 시 이메일
알림**을 설정한다. 콘솔 조작만으로 되는 일회성 설정이라 `deploy/setup.sh`(VM 안에서
도는 스크립트)의 범위가 아니라 `deploy/README.md`의 VM 생성 단계 근처에 안내로 넣는다.

여기서 한 단계 더 나아가 **AWS Budgets Actions**(예산 액션)를 함께 설정한다 — 임계값을
넘으면 지정한 EC2 인스턴스를 정지(`stop`)할 수 있는 기능인데, 실행 방식을 **자동
실행이 아니라 "수동 승인"으로 고정한다**: 이메일에 "실행" 링크가 오고, 사용자가 직접
클릭해야 실제로 인스턴스가 멈춘다.

**자동 실행 대신 수동 승인을 선택한 이유:** 이 서버의 `daemon.service`는 열린 포지션의
손절/익절을 실시간 감시한다(로드맵 문서에 이미 기록된 위험 — 서버/PC가 꺼지면 그
감시가 완전히 멈춰 포지션이 무방비로 노출됨). 예산 임계값을 넘었다고 해서 열린
포지션이 있는지 없는지는 AWS가 알 수 없으므로, 그 판단은 사람이 직접 해야 한다.
수동 승인 방식이면 알림은 즉시 오되, 실제 정지는 사용자가 라이브 전략 상태를 확인한
뒤 결정할 수 있다.

**구성 요소(런북에 명시):**
1. IAM 역할 하나 생성 — Budgets 서비스가 이 역할을 assume해 대상 인스턴스에
   `ec2:StopInstances`를 호출할 수 있는 권한만 부여(최소 권한, 다른 EC2 동작 불가).
2. AWS Budgets 콘솔에서 예산(월 $20) + 액션(대상: EC2 인스턴스, 타입: 정지, 승인
   방식: 수동) 생성.
3. 정지 후 재개는 EC2 콘솔에서 수동으로 `start`(Elastic IP가 그대로 붙어있으므로
   업비트 화이트리스트 재등록은 불필요, 결정2).

**한계(런북에 명시):** 인스턴스를 정지해도 Elastic IP(월 ~$3.6)와 EBS 스토리지(월
~$1.6) 요금은 계속 나간다 — 가장 큰 비중(인스턴스 시간당 요금)만 막을 뿐 완전한 $0은
아니다.

## 변경 파일

- `deploy/README.md`(수정) — "1. Oracle Cloud VM 생성" 섹션을 "1. AWS EC2 인스턴스
  생성"으로 전면 재작성(리전/인스턴스타입/AMI/스토리지/보안그룹/키페어/Elastic IP,
  결정 1·2·3·4). AWS Budgets 알림 설정 단계 추가(결정5). 기존 "7. Oracle이 안 되면:
  다른 클라우드로" 섹션은 이제 AWS가 주 경로가 됐으므로, "다른 클라우드로 이전하고
  싶다면" 문구로 갱신(내용 골자는 유지 — 스크립트가 클라우드 무관이라는 사실은
  그대로).
- 코드/테스트 변경 없음 — `deploy/setup.sh`, `deploy/update.sh`, systemd 유닛,
  `backend/main.py`의 `ALLOWED_ORIGIN` 처리 전부 이미 클라우드 무관하게 동작하므로
  손댈 필요가 없다.

## 에러 처리

- `deploy/setup.sh` 자체의 에러 처리는 2026-08-14 스펙 그대로(변경 없음).
- 런북 단계에서 흔히 겪을 문제(EC2 키페어 권한 오류, 보안 그룹에서 SSH를 빠뜨려
  접속 불가, Elastic IP를 인스턴스에 연결하지 않아 IP가 여전히 바뀌는 경우)를
  각 단계 옆에 "흔한 실수" 각주로 명시한다.

## 테스트 전략

인프라 문서 변경이라 자동화된 테스트 대상이 없다(2026-08-14 스펙의 결정4 관련 테스트는
이미 존재하고 이번 변경과 무관). 검증은 실제 배포 시 사용자가 런북을 따라가며 하는
수동 스모크 체크리스트로 한다 — 기존 2026-08-14 스펙의 "배포 후 체크리스트"를 그대로
쓰되, 5번 항목("공인 IP를 업비트 화이트리스트에 등록")이 이번엔 Elastic IP 주소가
된다는 점만 다르다.

## 자기 검토(스펙 완성도)

- **플레이스홀더 없음** — 5개 결정 각각 구체적 값(리전/인스턴스타입/스토리지 크기/
  예산 임계값)을 명시했다.
- **내부 정합성**: 결정3(보안 그룹에서 SSH만 개방)은 2026-08-14 스펙 결정3(Tailscale
  전용, ufw 이중 방어)과 계층만 다를 뿐(AWS 레벨 vs OS 레벨) 같은 원칙이다 — 모순
  없음.
- **범위 경계 재확인**: `deploy/setup.sh`/`update.sh`/systemd 유닛/`backend/main.py`
  중 어느 것도 변경 파일 목록에 없다 — 실제로 이번 스펙의 유일한 변경은
  `deploy/README.md` 문서뿐이다.
- **하위호환 확인**: 해당 없음(코드 변경이 없으므로 회귀 대상 자체가 없음).
- **가장 리스크가 큰 항목 식별**: 결정2(Elastic IP 미연결 시 IP가 계속 바뀌는 상황)와
  결정3(보안 그룹에서 SSH를 빠뜨리면 아예 접속 불가)이 가장 흔한 실수 지점이다 —
  런북에 두 항목 모두 완료 확인 체크포인트를 넣는다. 결정5(Budgets Actions)는
  "자동 정지"가 열린 포지션의 손절/익절 감시를 함께 끊을 수 있다는 위험이 있어,
  사용자와 상의해 의도적으로 수동 승인 방식으로 확정했다 — 자동 실행으로 바꾸고
  싶어지더라도 이 트레이드오프를 다시 확인할 것.
