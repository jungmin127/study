# 업비트 과거 시세 로컬 적재 파이프라인 설계

- 작성일: 2026-07-11
- 상태: 승인 대기 (사용자 리뷰 전)

## 배경 및 목적

백테스팅을 통한 전략 수립과 향후 자동매매 개발을 목표로 한다. 이를 위해서는 업비트 과거 시세 데이터가 필요한데, 매번 API(혹은 Claude 대화를 통한 조회)를 호출하면 다음 문제가 있다.

- 반복 호출로 인한 비효율 (같은 데이터를 매번 다시 받아옴)
- Claude Code 대화 컨텍스트에 원본 시세 데이터가 그대로 들어가면서 발생하는 토큰 소모 — 특히 전략 개발은 같은 데이터로 반복 테스트하는 경우가 많아 누적 비용이 커짐

**이번 스펙의 목적**: 과거 시세를 한 번 수집해 로컬에 저장하고, 이후 백테스팅은 로컬 저장소를 조회하는 방식으로 전환하여 위 문제를 해소한다.

## 스코프 분리 (중요)

이 프로젝트는 아래 두 개의 독립된 서브프로젝트로 나뉜다.

1. **서브프로젝트 1 — 로컬 시세 적재 파이프라인 (본 스펙의 범위)**: 개인 PC에서 과거 시세를 수집·저장. 백테스팅/전략 개발용. PC가 켜져 있을 때만 동작하면 됨.
2. **서브프로젝트 2 — 자동매매 엔진 (별도 스펙, 향후 브레인스토밍)**: 서브프로젝트 1의 백테스팅으로 검증된 룰/모델 기반 threshold를 실제로 실행. **PC가 꺼져 있어도 동작해야 하므로 클라우드/VPS 등 상시 구동 인프라에 별도로 배포**해야 한다. 데이터/전략이 검증된 이후 별도로 설계한다.

본 문서는 서브프로젝트 1만 다룬다.

## 요구사항 요약 (브레인스토밍 결과)

| 항목 | 결정 사항 |

| 타임프레임 | 일봉/시간봉 중심 |

| 자동매매 연동 | 이번 스펙 범위 아님 (서브프로젝트 2에서 별도 설계, 상시 구동 인프라 필요) |

## 아키텍처

Claude/CLI와 무관하게 독립적으로 동작하는 순수 Python 프로젝트로 구성한다.

- **데이터 수집**: Python 스크립트가 Upbit 공개 REST API(캔들 조회는 인증 불필요)를 직접 호출. Claude나 `upbit` CLI를 매 실행마다 거치지 않음.
- **저장소**: 서버 설치가 필요 없는 DuckDB 파일 하나(`data/market_data.duckdb`). 백테스팅 시 SQL로 바로 쿼리 가능.
- **오케스트레이션**: Windows 작업 스케줄러가 PC가 켜져 있을 때 주기적으로 `python ingest.py`를 트리거. 수동 실행도 언제든 가능.
- Airflow는 검토했으나 기각: Windows 네이티브 지원이 약해 Docker/WSL2가 사실상 필수인데 사용 경험이 없고, 현재 데이터 규모(소수 코인 + 일/시간봉)에 비해 인프라(웹서버, 스케줄러, 메타DB)가 과함. Prefect는 대안으로 검토했으나, 지금 규모에서는 Python 스크립트 + 작업 스케줄러로 충분하다고 판단. 파이프라인이 복잡해지면(코인/타임프레임 대폭 확장, 여러 단계 의존성 등) Prefect로 전환을 재검토한다.

## 왜 이 구조가 토큰 소모 목적에 부합하는가

- 기존 방식(Claude에게 매번 시세 조회 요청): 캔들 데이터 원본이 대화 컨텍스트에 그대로 들어감. 캔들 1개당 대략 150~250 tokens 수준이며, 코인 1개 1년치 일봉(365개)만 해도 수만 tokens, 여러 코인·여러 년치를 반복 조회하면 누적 비용이 커짐.
- 로컬 DuckDB 구조: 적재는 Claude 개입 없이 백그라운드 스크립트가 처리. Claude는 원본 데이터를 직접 보는 대신 "DuckDB를 쿼리하는 코드"를 작성/실행하고, 백테스팅 결과(수익률, MDD, 샤프비율 등 요약 지표)만 컨텍스트에 들어옴. 대화당 토큰 소모가 원본 데이터 규모와 무관하게 일정 수준으로 유지됨.
- 정확한 tokens/request 수치는 데이터 포맷·요약 방식에 따라 달라지므로 보장할 수 없으나, 방향성(반복 조회 비용을 원천 제거)은 명확하다.

## 구성 요소

- **`config/markets.yaml`**: 적재할 마켓/타임프레임/히스토리 시작일 목록. 코인 추가·삭제는 이 파일만 수정하면 되고 코드 변경은 불필요.
- **`upbit_client.py`**: Upbit 공개 캔들 API(`/v1/candles/days`, `/v1/candles/minutes/{unit}`) 래퍼. `to` 파라미터로 페이지네이션(최대 200개/요청 제한 준수), 초당 요청 제한 대응 딜레이 포함.
- **`db.py`**: DuckDB 스키마 정의 및 upsert 로직. Primary key `(market, timeframe, candle_time)`로 중복 방지.
- **`ingest.py`**: 진입점 스크립트. `config/markets.yaml`을 읽어 마켓별로 DB에 저장된 마지막 시각을 확인 → 그 이후~현재까지 누락분만 수집 → upsert.
- **`logs/`**: 실행 로그(마켓별 적재 건수, 실패 내역 등).

## 데이터 흐름

1. 작업 스케줄러(또는 수동 실행)가 `python ingest.py`를 트리거한다.
2. 마켓/타임프레임별로 DuckDB에서 `MAX(candle_time)`을 조회한다.
3. 첫 실행이면 설정된 기본 시작일부터, 아니면 마지막 저장 시각 이후부터 캔들을 수집한다.
4. 아직 마감되지 않은(진행 중인) 캔들은 저장하지 않는다 — 이후 값이 바뀌는 것을 방지하기 위함.
5. 캔들을 DuckDB에 upsert한다 (재실행해도 중복이 생기지 않음 → PC를 며칠 꺼놨다 켜도 안전하게 catch-up 가능).
6. 실행 결과를 로그로 남긴다.

## 에러 처리

- API 요청 실패 시 지수 백오프로 최대 3회 재시도. 그래도 실패하면 해당 마켓만 skip하고 로그에 기록 — 다음 실행 때 마지막 저장 시각 기준으로 자동으로 이어서 채워지므로 데이터 유실이 없다.
- `config/markets.yaml`에 존재하지 않는 마켓 코드가 있으면 실행 시작 시 검증하여 명확한 에러로 즉시 실패시킨다.

## 테스트

- 페이지네이션/backfill 로직에 대한 단위 테스트 (Upbit API 모킹)
- upsert 멱등성 테스트 — 같은 구간을 재실행해도 중복 행이 생기지 않는지 확인
- 실제 마켓 1개, 짧은 최근 구간으로 수동 스모크 테스트 — DuckDB에 정상 적재되는지 확인
