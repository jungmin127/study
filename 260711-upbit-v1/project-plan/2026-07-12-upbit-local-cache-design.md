# 업비트 로컬 시세 캐시 설계 (간소화 버전)

- 작성일: 2026-07-12
- 상태: 승인 대기 (사용자 리뷰 전)
- 대체 문서: `2026-07-11-market-data-ingestion-design.md` (DuckDB + Windows 작업 스케줄러 기반, 이 문서로 대체됨)

## 배경 및 목적

전날(`2026-07-11-market-data-ingestion-design.md`) DuckDB + Windows 작업 스케줄러 + `config/markets.yaml` 기반의 상시 적재 파이프라인을 설계했으나, 다음 이유로 범위를 재검토했다.

- 핵심 목표는 "백테스팅을 통한 매매 룰 설정과 모델링"이며, 시세 적재 자체는 그 목표를 위한 수단일 뿐이다. 적재 과정에 별도 오케스트레이션(스케줄러)과 설정 파일 레이어를 두는 것은 이 목표에 비해 과한 인프라였다.
- 기존에 중단했던 `backtesting_1` 프로젝트(`C:\Users\jungm\project\backtesting_1`)를 확인한 결과, Binance 데이터에 대해 이미 "lazy fetch + Parquet 로컬 캐시" 패턴(`backend/app/services/data_service.py`)이 검증되어 있었다. 같은 패턴을 Upbit에 적용하면 별도 스케줄러 없이도 반복 API 호출과 Claude 토큰 소모 문제를 동일하게 해결할 수 있다.

**이번 스펙의 목적**: Upbit 과거 시세를 함수 호출 시점에 필요한 만큼만 받아와 로컬 Parquet 캐시에 쌓는 최소 구성의 모듈을 만든다. 스케줄러, 설정 파일, DB 서버를 두지 않는다.

## 이전 설계와의 차이

| 항목 | 이전 설계(2026-07-11) | 이번 설계 |
|---|---|---|
| 적재 시점 | Windows 작업 스케줄러가 주기적으로 사전 적재 | 백테스팅 스크립트가 데이터를 요청하는 순간(lazy fetch) |
| 저장소 | DuckDB 단일 파일 | 마켓·타임프레임별 Parquet 파일 |
| 대상 마켓/타임프레임 지정 | `config/markets.yaml` | 함수 호출 인자로 그때그때 지정 (설정 파일 없음) |
| 오케스트레이션 | Windows 작업 스케줄러 | 없음 |
| 부분 캐시 처리 | 해당 없음(항상 전체를 마지막 저장 시각 이후로 이어서 적재) | 요청 구간 중 캐시에 없는 부분만 계산해 추가 호출 |

## 스코프 분리 (변경 없음)

- **서브프로젝트 1 — 로컬 시세 캐시 (본 스펙의 범위)**: 개인 PC에서 백테스팅용 과거 시세를 필요할 때 가져와 캐싱. PC가 켜져 있을 때만 동작.
- **서브프로젝트 2 — 자동매매 엔진 (별도 스펙)**: 상시 구동 인프라 필요, 별도 설계.

## 아키텍처

- 단일 모듈 `upbit_data_service.py` — `backtesting_1`의 `data_service.py`를 Upbit 캔들 API에 맞게 변형.
- **데이터 수집**: Upbit 공개 캔들 API(`/v1/candles/days`, `/v1/candles/minutes/{unit}`, 인증 불필요)를 `httpx`로 직접 호출. Claude나 `upbit` CLI를 거치지 않음.
- **저장소**: `data/cache/ohlcv/{market}_{timeframe}.parquet` (예: `KRW-BTC_days.parquet`, `KRW-BTC_minutes60.parquet`). 마켓·타임프레임 조합마다 파일 하나.
- **오케스트레이션**: 없음. 백테스팅 스크립트가 `get_candles()`를 호출하는 시점이 곧 적재 시점.

## 인터페이스

```python
def get_candles(
    market: str,       # "KRW-BTC" 형식
    timeframe: str,     # Upbit 캔들 API 단위: "days" | "minutes60" 등
    start: datetime,
    end: datetime,
) -> pd.DataFrame:
    """
    반환 컬럼: [candle_time, open, high, low, close, volume]
    마감된 캔들만 포함 (진행 중인 캔들 제외)
    """
```

대상 마켓/타임프레임을 미리 등록하는 설정 파일은 두지 않는다. 새 코인을 백테스팅하고 싶으면 호출부에서 문자열만 바꾸면 된다.

## 데이터 흐름

1. `get_candles(market, timeframe, start, end)` 호출.
2. `data/cache/ohlcv/{market}_{timeframe}.parquet` 로드 (파일이 없으면 빈 캐시로 취급).
3. 요청 구간 `[start, end]` 중 캐시가 커버하지 못하는 부분을 계산한다.
   - 캐시가 아예 없음 → 전체 구간이 부족분.
   - 캐시가 앞부분만 있음(예: 캐시는 1월까지, 요청은 2월까지) → 캐시 끝 이후만 부족분.
   - 캐시가 뒷부분만 있음(과거로 더 거슬러 올라가는 요청) → 캐시 시작 이전만 부족분.
   - 캐시가 전체를 커버 → API 호출 없이 바로 4번으로.
4. 부족분에 대해서만 Upbit 캔들 API를 페이지네이션 호출 (최대 200개/요청, 초당 요청 제한 대응 딜레이 포함, 지수 백오프 재시도).
5. 아직 마감되지 않은(진행 중인) 최신 캔들은 응답에서 제외 — 이후 값이 바뀌는 것을 방지.
6. 새로 받은 데이터를 기존 캐시와 `candle_time` 기준 중복 제거 후 병합, Parquet에 재저장.
7. 요청 구간 `[start, end]`에 해당하는 부분만 잘라서 DataFrame으로 반환.

## 에러 처리

- API 요청 실패 시 지수 백오프로 최대 3회 재시도 (429 응답은 더 길게 대기). 3회 모두 실패하면 예외를 그대로 호출부로 전파한다 — 백테스팅 스크립트가 스킵할지 중단할지 직접 판단.
- 존재하지 않는 마켓 코드에 대한 사전 검증은 하지 않는다. 설정 파일이 없으므로 검증 대상 목록 자체가 없고, Upbit API가 반환하는 에러를 그대로 예외로 전파하는 것으로 충분하다.

## 테스트

- 부분 캐시 겹침 계산 로직 단위 테스트 (캐시 없음 / 앞부분만 있음 / 뒷부분만 있음 / 완전 커버 각 케이스)
- 캐시 병합 시 중복 제거(멱등성) 테스트 — 같은 구간을 반복 요청해도 중복 행이 생기지 않는지
- 실제 마켓 1개, 짧은 최근 구간으로 수동 스모크 테스트 — Parquet에 정상 캐싱되는지 확인
